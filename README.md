# AI时代的自动化建模Skill

**一套面向不同题目和领域的轻量数学建模 Skill：先把基线做对，再让模型、论文和图表形成有证据的观点。**

内容是通用数学建模工作流。它可以用于完整比赛，也可以只处理某一问、检查一个模型或修改一段论文。用于比赛时，以当届官方题面、规则和模板为准。

整个文件夹就是工具包，保留隐藏的 `.agents` 和 `.vscode` 后即可转发。运行不依赖旧 Skill 或原始参考仓库；实际计算仍需要可用的本机环境。

## 快速开始

1. **解压完整文件夹。** 用 VS Code 或能够读写本地文件、执行终端命令的 AI 工具打开它，不在压缩包内运行。
2. **首次使用先配置环境。** 把下面这句话交给 Agent；已有可用环境就复用，只做文稿阅读时不必先装软件。

   > 请读取 `Agent环境配置指南.md`，检查并配置这台电脑的竞赛环境。复用已有工具，仅补必要缺项，实际验证计算、中文绘图和 LaTeX 编译与预览；完成后简短报告结果。

3. **指定任务和输出目录。** 让 AI 读取入口，再提供题面、数据和要求。

   > 请读取 `.agents/skills/mathorcup-modeling/SKILL.md`，完成我的数学建模任务。先核对题意并验收基线，再根据证据比较改进。论文使用 LaTeX，所有产物保存到我指定的项目目录。

操作细节见 [使用说明](使用说明.md)，让 Agent 配置机器时用 [Agent 环境配置指南](Agent环境配置指南.md)。纯聊天工具若不能访问文件或运行程序，只能提供分析建议，不能完成本包的执行与验收。

## 我的升级思路

在使用网络上开源的skill时，我发现了如下的问题：流程太重、表达太保守：AI 花很多篇幅解释自己做了哪些检查，真正的观点反而不突出；论文和图表也容易落入固定套路。原先过于重型的门禁，反而限制了先进ai的思考，对于ai深度赋能的数学建模比赛显然是不利的，但是我并没有全然抛弃原来的东西，比如基线模型的编写是要确保正确的，所以基线模型提示词被完整保留。总而言之，我希望提升AI数学建模的上限，充分发挥模型能力。同时我认为，原先“建模手+论文手+编程手”的思路已经落后，现在可能是短时间内让三个人迭代数个版本，互相赛马，最后进行必要的人工校验。

因此，这次选择从头重构入口，再把已经验证过的方法和必要检查迁回来。重点是减少无效约束，让精力回到理解问题、寻找突破口和解释结果上。

| 原来的问题 | 这次的改法 | 希望得到的结果 |
|---|---|---|
| 启动就加载大量流程和参考 | 短入口统筹，参考文件按需读取，局部任务直接处理 | 把上下文留给当前题目 |
| 担心出错，论文充满防御性表述 | 关键验证实际完成，正文只展开影响判断的证据 | 读者先看懂答案、理由和价值 |
| 轻量化后可能丢掉可靠基线 | 迁回旧版方法库和可运行基线，每题重新验收适用性 | 改进有可信的比较起点 |
| 图文格式固定，容易写成模板 | 允许重组论证、调整图型、布局与配色 | 图文围绕本题发现组织 |
| 队友环境不同，说明太长且不易执行 | 一个文件夹交接，一份 Agent 指南负责检测、补缺和验收 | 每个人都能计算、编辑 LaTeX 和查看 PDF |

这里的“轻量”主要指指令和协作负担。必要的建模、实验与验证仍然要做；复杂方法只要能回答问题、带来可靠收益，也可以采用。

## 已落地的创新与优化

### 1. 基线可复用，正确性逐题验收

当前包内有六类方法指南，以及均值、含截距 OLS、朴素预测、移动均值、容量设施选址五个可运行基线。指南和实现分别标明，不把方法名称当成已经写好的程序。

基线需要同时满足三个条件：回答当前问题、实现符合数学定义、真实输入上的结果通过必要核验。旧代码经过测试，也不能替代当前题目的参数含义、单位、边界和信息可见时点检查。验收后保留基线，在相同口径下比较改进。

入口：[基线与方法库](.agents/skills/mathorcup-modeling/references/baselines.md)。

### 2. 将验证深度与正文篇幅分开

关键验证决定能否相信结论，正文篇幅取决于它对论证有多大作用。训练测试隔离、优化约束、关键参数解释等问题必须处理；常规检查通过后可以一句带过，详细记录留在支撑材料。

写作从建模早期开始：先形成“本文判断什么、依据是什么”的草稿，再反向发现缺少的实验。允许重写章节和图文结构，不要求每问机械重复同一套小标题，也不靠不断添加限制语来显得严谨。

入口：[实验与判断](.agents/skills/mathorcup-modeling/references/experiments.md)、[表达与绘图](.agents/skills/mathorcup-modeling/references/expression.md)。

### 3. 保留四种职能，减少形式化协作

| 职能 | 主要责任 |
|---|---|
| 建模手 | 解释题意，定义变量、假设、目标和约束，验收基线并提出改进 |
| 编程手 | 实现真实计算，核对数据接口、结果和复现过程 |
| 写作手 | 早期组织观点与证据，提出实验需求，完成图文表达 |
| 评委 | 检查是否答题、比较是否成立，以及最影响结论的问题 |

主 Agent 负责统筹和最终核验。这是四种职责，不要求四个代理常驻；是否委派取决于任务价值、平台能力和当前协作规则。关键疑点优先独立核验，评审意见再回到原文、代码和结果裁决，不能因其来自“评委”角色就直接接受。

### 4. 图表承担解释，工具保持通用

通用绘图使用 **Matplotlib + Seaborn**，包内辅助函数处理中文字体、标注和 PNG／PDF／SVG 导出。先明确图要解释的关系，再选择图型和布局；可以尝试不同表达，但没有固定图数、配色或期刊风格要求。

真实数据决定几何和数值，导出的图还要放到论文实际尺寸检查。常见统计图、机制图和结果对照不需要再安装整套绘图软件。

入口：[绘图工具](.agents/skills/mathorcup-modeling/references/figures.md)。

### 5. 把交接落实到可运行文件

统一交付 LaTeX 源文件、实际使用的引用和图表素材、编译后的 PDF，以及计算代码和结果。每位使用者都需要具备编辑、编译和预览能力，不另建 Word 文稿路线。

环境指南面向 Agent 执行：先找到真实解释器，再检查依赖并做实际验收。VS Code 是编辑器，Python 负责计算，XeLaTeX 负责论文编译；三者职责分别说明。已有可用环境继续使用，缺什么补什么，不复制他人的虚拟环境，也不默认升级软件。

入口：[交付与环境](.agents/skills/mathorcup-modeling/references/delivery.md)。

## 从实际使用中保留的经验

**先对齐问题，再比较数字。** 两份答案不同，先查数据、参数的物理位置、变量定义、约束、初终状态与时间口径。目标值更低或指标更高，只有在比较条件一致时才说明改进。

**简单方案也可能赢。** 更多特征、更复杂的模型或更激进的清洗不必然有效。候选方案要用同一评价口径比较，没有稳定收益时回到已验收版本。

**总体高分可能掩盖关键失败。** 预测误差、少数类识别、约束可行性和业务决策分别关注什么，需要由题目决定。论文应解释错误集中在哪里，以及它是否改变推荐。

**迭代要保留证据边界。** 看过测试结果后再改方案，不能把同一批数据重新称为全新的独立验证。版本应记录改了什么、凭什么采用，以及何时停止尝试。

这些经验进入通用工作方法；某道题的参数、标签比例、最佳模型和具体成绩留在对应项目，不固化为以后所有比赛的规定。

## 人工介入与自主推进

题意存在会改变答案的歧义、缺少关键价值偏好，或需要超出已授权范围时，Agent 应把分歧、证据和影响讲清楚，请用户决定。常规实现、低成本实验和文稿修改在授权范围内自主推进，不逐步索要确认。

如果希望先控制题意理解，可以在任务开头明确要求：**“先提交题意理解和关键假设，等我确认后再建模。”** 这是可指定的人工断点；当前包没有独立的断点控制界面，也没有强制逐阶段审批。
